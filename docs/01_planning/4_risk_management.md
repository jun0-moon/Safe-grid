# 4. 위험 관리 (Risk Management)

## 4.1. 위험 관리 개요

본 프로젝트는 다수의 스마트폰에서 발생하는 실시간 위치 데이터를 처리해야 하므로, 대용량 트래픽으로 인한 시스템 과부하 및 일정 지연 등의 위험 요소가 존재합니다. 프로젝트의 안정적인 완수를 위해 예상되는 주요 위험 요소를 식별하고 선제적인 대응 방안(Mitigation Plan)을 수립합니다.

## 4.2. 주요 위험 요소 및 대응 방안

### ① 기술적 위험: 대용량 트래픽으로 인한 DB 및 서버 과부하

- **위험 내용:** 초당 수백~수천 건의 가상 GPS 데이터가 동시에 인입될 경우, 메인 DB(PostgreSQL)에 병목 현상이 발생하여 서버가 다운되거나 응답이 지연될 수 있습니다.
- **대응 방안 (Mitigation):** \* 인메모리 데이터 스토어인 **Redis를 도입**하여 실시간 위치 데이터를 1차적으로 캐싱(Caching)하고, 일정 주기로 메인 DB에 일괄 업데이트(Batch Update)하는 아키텍처를 설계합니다.
  - 프로젝트 초기 단계(10주 차)부터 **JMeter를 활용한 스트레스 테스트**를 수행하여 서버의 한계치를 미리 파악하고 최적화합니다.

### ② 기술적 위험: 공간 데이터 연산(PostGIS) 쿼리 지연

- **위험 내용:** 복잡한 골목길 폴리곤(Polygon) 데이터와 수만 개의 위치 포인트(Point) 데이터를 실시간으로 대조하여 밀집도를 계산할 때, 공간 연산 쿼리(ST_Contains 등)의 처리 속도가 저하될 수 있습니다.
- **대응 방안 (Mitigation):** \* 공간 데이터에 특화된 **공간 인덱스(Spatial Index, GiST 등)**를 데이터베이스에 적용하여 검색 속도를 획기적으로 개선합니다.
  - 계산이 복잡한 우회 경로 탐색은 클라이언트(웹 브라우저)의 자원을 일부 활용하거나, 캐싱된 결과값을 재사용하도록 로직을 분산시킵니다.

### ③ 일정 위험: 프론트엔드와 백엔드 API 연동 지연

- **위험 내용:** 백엔드 API 개발이 완료될 때까지 프론트엔드 개발자가 화면 연동 작업을 시작하지 못해 전체 개발 일정이 지연될 수 있습니다.
- **대응 방안 (Mitigation):** \* 기획 단계(7주 차)에서 **API 명세서(Swagger 또는 Notion 활용)를 우선적으로 확정**합니다.
  - 프론트엔드 파트는 더미 JSON 데이터(Mock Data)를 활용하여 UI/UX 및 지도 시각화 작업을 백엔드 개발과 독립적이고 병렬적으로 진행합니다.

### ④ 협업 위험: 팀원 간 소통 부재 및 업무 누락

- **위험 내용:** 4인 팀 단위 작업 시, 각자 맡은 파트의 진척도가 공유되지 않거나 깃허브(GitHub) 병합 과정에서 치명적인 코드 충돌이 발생할 수 있습니다.
- **대응 방안 (Mitigation):** \* 매주 지정된 시간에 디스코드(Discord)를 통한 **정기 스프린트 회의**를 진행하고 진척도를 점검합니다.
  - 엄격한 **Git Flow 전략**을 사용하여 메인 브랜치 직접 Push를 금지하고, 반드시 Pull Request(PR)와 팀원 1명 이상의 코드 리뷰(Code Review)를 거친 후 병합하도록 규칙을 강제합니다.
